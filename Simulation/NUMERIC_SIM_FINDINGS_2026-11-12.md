## 1. V13：写请求脉冲太窄，所有引擎写操作被当成读（已修，ROM 级）

### 1.1 机理

S02 的写/读选择信号 `WE_S` 不是 `WE` 的简单延迟，而是**限定后的延迟**：
`WE_S <= any(REQ & WE)`（U2009 74HC74 + U12011/U12010 与或网络）。
引擎的控制寄存器比状态寄存器**晚一个状态**，所以 `E_ADDR_OUT` 的 ROM 字
（REQ=1,WE=1）只在 `E_WRITE` 的第一个时钟有效，第二个时钟就变成
`E_WRITE` 的字（原来 REQ=0）。

结果：计时控制器进 SETUP 时 `WE_S` 已经是 0 → 写周期被当成**读周期**执行，
引擎却把这个读周期的 ACK 当成"写完成"继续走。

实测快照（`tb_wr_snap.log`）：请求只维持 1 拍，TS 走的是
`SETUP→WAIT→CAPTURE`（读），nWE 全程为 1。

### 1.2 修复

`E_ADDR_OUT` 和 `E_WRITE` **两个状态的字都保持 `mem_req=1`、`mem_we=1`、
`add_sel=OUT`**，即 REQ 在整个等待 ACK 期间连续有效。

### 1.3 验证

```
修复前：Write-cycle owner: C1=0 C2=0 FC=0 POOL=3102
修复后：Write-cycle owner: C1=576 C2=100 FC=72 POOL=3102   （本版）
最终  ：Write-cycle owner: C1=576 C2=100 FC=72 POOL=1552
```
C1=576=24×24 ✓，C2=100=10×10 ✓，FC=32(FC1)+40(FC2 四字节) ✓。

## 2. V14：池化重复写（已修，计时 ROM 级）

### 2.1 机理

池化在写完成后仍保持 REQ（电平敏感、允许背靠背传输），而 `WE_S` 是
`any(REQ&WE)` 的延迟，写结束后还会多保持一拍。控制器回到 IDLE 时看到
`WE_S=1` 就**又启动一次写**：1552 个池化输出产生 3102 个写周期，
多出来的 1151 次落在页 1（CONV1_OUT）、399 次落在页 3（CONV2_OUT），
而且此时输出缓冲器已关闭，写进去的是 `z`——**把卷积输出整片污染成 x**。

### 2.2 修复

计时 ROM 的 DONE 状态：如果是写周期且 `WE_S` 仍为 1，先进 GAP_WE 状态等
`WE_S` 落下再回 IDLE。FC2 的四字节连写是合法地保持 WE 的，所以 GAP_WE 用
`WAIT_MATCH`（写周期 WAITV=15）做超时，不会死锁。

### 2.3 验证

```
SEL at WE-rise: 1:576 2:1152 3:100 4:400 5:32 6:40 31:2
→ 页 1 只有 C1 的 576 次，页 2/4 正好是池化的 1152/400 次，无重复
C1OUT: nonzero=265 x/z=0   （此前 1151 字节是 x）
```

## 3. V14b：池化在 ACK 后一拍采样，数据已被释放（已修，计时 ROM 级）

池化的 MAX 寄存器在 `S_CP` 状态（ACK 之后**下一个时钟**）采样总线。
原计时 ROM 在 CAPTURE 下一拍（RELEASE）就把 `nCE/nOE` 拉高，总线变 `z`，
于是每个窗口第一个值被锁成 `x`，MAX 从此永远是 `x`。

修复：读周期在 RELEASE 状态**继续保持 `nCE=0, nOE=0` 一拍**，DONE 才释放。
验证：`MAX` 变成有效值（`ae`），P1OUT：`1152` 字节、`x/z=0`。

## 4. V15：lane 计数器 /PE 缺 ACC_EN（原理图缺陷，必须改板）

### 4.1 现象

加 V13 修复后，引擎能发写周期，但**写进去的数据恒为 0**：

```
[C1W] n=20 t=26288375000 ACC=00000000 QVAL=00 Q=00 OUT=00
MAC: pulses=14403  A!=0:3357  B!=0:12675  P1!=0:2936
ACC_LD pulses=0                      ← 累加器一次都没装载
```

### 4.2 根因（已用波形证实）

四个引擎都是 4 lane 并行 MAC：4 个 LUT 乘法器同时算，乘积相加成 `PSUM`，
累加器每 4 个 MAC 装载一次：

```
ACC_LD   = ACC_EN & LANE_LAST        (74HC08, p1=ACC_EN p2=LANE_LAST)
LANE_LAST= LANE0 & LANE1             (4 位计数器计到 3)
LANE_PE_N= ~(LANE0 & LANE1)          ← 少了 ACC_EN！
```

74HC161 计数器：`CEP=CET=ACC_EN`（只在 E_ACC 状态计数），`/PE=LANE_PE_N`。
计数序列在 E_ACC 期间是 **0,1,2,0,1,2…**：第 3 个 MAC 结束时 Q 才到 3，
但下一个时钟 `/PE` 立刻把它清 0，所以 **Q=3 永远不与 E_ACC 重叠**，
`ACC_LD` 永远为 0，ACC 永远是 0。

波形证据（`[MT]`，状态 7 = E_ACC）：
```
t=24886375000 ST=00111 q=0010 PE_N=1 ACC_EN=1
t=24886500000 ST=00010 q=0011 PE_N=0     ← 离开 E_ACC 后才到 3
t=24886625000 ST=00011 q=0000            ← 立刻被清 0
```
其它计数器（KX/KY/OX/OY）都写成 `~(LAST & EN)`，唯独 lane 计数器漏了 EN。

### 4.3 四个位置（同一子电路复制了四次）

| 板 | 计数器 | /PE 门 | 应改为 |
|---|---|---|---|
| S07 Conv1 | U7140 (74HC161) | U7022 第 4 门 | `~(LANE_LAST & ACC_EN)` |
| S08 Conv2 | U8141 | U8142 第 1 门 | 同上 |
| S09 FC1 | U9127 | U9015 第 4 门 | 同上 |
| S09 FC2 | U9209 | U9215 第 4 门 | 同上 |

### 4.4 已做的临时验证

在 `cnn74_top.v` 里加 RTL ECO（`assign LANE_PE_N = RAW | ~ACC_EN`）后：
```
ACC_LD pulses=3600 (14403/4)
ACC: clocks!=0=122897
[C1W] n=200 ACC=0002eb2a QVAL=ff Q=ff OUT=ff DBUS=ff   ← 有真实数据
```

> 注意：`cnn74_top.v` 里的 ECO 只是**仿真用**，不是修复方案。
> 板上必须有等效的电路改动，否则四块引擎板全部输出 0。

## 5. V16：乘法器是 8×8 无符号，而 V2 契约要求有符号权重（架构决策）

### 5.1 事实

- LUT ROM 地址 = `{A[7:0], B[7:0]}`，输出 16 位乘积；
- 当前映像（`gen_lut.py`）是**无符号** `A*B`，65536 项全部匹配无符号乘法；
- 4 乘积相加（S12+S34）是 **16 位无符号加法 + 进位扩展**（U7097 只取进位），
  累加器 U7103–U7110 在高位加 0，**没有符号扩展**；
- requant 却把 ACC 当 **signed 32 位**用（`ACC31=1 → Q=0`，`SAT_POS` 饱和）。

无符号乘法 + 无符号加法树 + 有符号判读，只能正确处理**非负乘积**。
V2 契约（`REQUANT_SIMPLE_V2.md`）要求对称 int8 权重（含负值），
负积在 16 位补码里是 0x8000..0xFFFF 的大正数，加法树会把它当正数累加：

```
4 个负积之和 = 真值 + 65536 × (负积个数)   ← 负积个数随窗口变化，无法校正
```

实测：C1OUT 大量 `0xFF`（饱和），FC1OUT 全 `0xFF`，logit 全错。

### 5.2 历史原因

`HW_ARCH_CONTRACT.md` 的 V1 设计是：权重存成 **偏移二进制** `w_code = w + 128`，
累加 RAW_SUM 和 SUM_X / SUM_W，最后在 requant 里做
`ACC = RAW_SUM - zp_w*SUM_X - zp_x*SUM_W + N*zp_x*zp_w + bias`（需要串行乘法器和
三个累加器）。V2 为了减芯片把这套修正全部删掉，但保留了"对称有符号权重"的量化契约
——两者不兼容。

### 5.3 三个可选修复方案

| 方案 | 内容 | 改板量 | 精度 |
|---|---|---|---|
| **A. 改量化契约（推荐先试）** | 权重限制为**非负** uint8（0..255，ZP=0），LUT 仍是无符号乘法；重新训练/导出 | **不改板** | 需实测，预计下降 |
| **B. 加常数偏置减法** | LUT 改成 `a*w + 32768`（一定非负、正好 16 位），每层在 requant 前减去 `32768*N`（N=每点 MAC 数：28/12/128），即给累加器加"预置常数"通路 | 每引擎 8 片 74HC157 + 常数（或 requant 加 32 位减法器） | 与 V2 相同 |
| **C. 把加法树改成有符号** | 每级加法的进位扩展改为符号扩展（2 个 XOR/级 + 高位符号线），ACC 高位补符号 | 每引擎 3–4 片 | 与 V2 相同 |

> 方案 A 最省事但精度未知；B/C 保持 97.5% 的 V2 精度但要改板。
> 建议顺序：先按 A 的假设跑通端到端（证明其余逻辑正确），再决定 B/C。

## 8. V17：卷积核计数器在补零期间被推进（原理图缺陷）

实测每个输出点的 MAC 数：

```
修复前: p0(MAC=28,LD=7) p1(MAC=25,LD=6) p2(MAC=25,LD=6) ...
修复后: p0(MAC=28,LD=7) p1(MAC=28,LD=7) p2(MAC=28,LD=7) ...
```

5×5 卷积 = 25 抽头，4 lane 分组需要 28 步（25 真实 + 3 补零）。
补零期间 `PAD_ACTIVE=1`、B 被强制为 0，但 KX/KY 计数器仍被 MAC_EN 推进
（计数 0→1→2→3），所以第一个点之后的对齐就错了：

```
t=24949625000 KX=000 PAD_A=1     ← 补零 1
t=24952375000 KX=001 PAD_A=1     ← 补零 2
t=24955125000 KX=010 PAD_A=1     ← 补零 3
t=24959500000 KX=011 PAD_A=0     ← 下一个点的第 1 个 MAC 从 KX=3 开始
```

结果：第 2 个点起只走 22 个真实抽头，权重覆盖错位。

修复：`KX_PE_N` / `KY_PE_N` 与 `PAD_ACTIVE` 相与（/PE 低有效，即
`/PE = ~(LAST & MAC_EN) & ~PAD_ACTIVE`）。位置：S07 U7021 第 1/2 门、
S08 U8019 第 1/2 门。加了 RTL ECO 后每点都是 28 MAC / 7 次装载，ACC_LD=4032=576×7。

## 10. 方案 A 精度实测（非负权重）

